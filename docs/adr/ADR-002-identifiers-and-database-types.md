# ADR-002: uuid entity identifiers, BIGINT surrogate key for the fact table

## Context

Phase 2 replaced `TEXT` primary keys. Two different pressures apply:

- **Entities** (Product, ProductIdentifier, Listing, ListingVariant, DataSource)
  are referenced from API responses, tests, and future external tooling. Random
  identifiers are fine; insert volume is low.
- **PriceObservation** is the high-volume fact table. Its key is embedded as a
  foreign key in `ObservationStatusEvent` and any future fact-adjacent tables.

Previously all ids were `String @id @default(uuid())` — stored as `TEXT`
(36+ bytes/row), including on the fact table.

## Decision

- Entity tables use `Uuid @id @default(uuid())` — Postgres `uuid`, 16 bytes,
  indexed natively, generated by `gen_random_uuid()`.
- `PriceObservation.id` is `BigInt @id @default(autoincrement())` — an 8-byte
  sequence. Benefits: sequential inserts append to the right edge of the btree
  (good locality, minimal page splits), roughly a quarter of the key width of a
  random uuid, and narrower FK joins from `ObservationStatusEvent` and future
  tables. The existing data was migrated by INSERT…SELECT ordered by
  `(observedAt, receivedAt)` so ids are ascending in observed-time order.
- API responses serialise `observationId` as a decimal string (JSON has no
  64-bit integer).

## Alternatives considered

- **uuidv7** — time-ordered uuids preserve insert locality and stay mergeable
  across writers. Chosen against: 16 vs 8 bytes, and Postgres 16 has no native
  `uuidv7()`; the value of distributed generation is speculative for a single
  Postgres writer.
- **ULID** — same trade-off as uuidv7, plus no native Postgres type (would
  store as TEXT, losing the width benefit).
- **Composite natural key `(listingId, receivedAt)`** — avoids a surrogate key
  but is not unique (two inserts may share a millisecond) and repeats a wide
  composite into every referencing table.
- **TEXT uuid status quo** — 36+ bytes per row and per FK; heavier indexes at
  fact-table scale.

## Consequences

- BigInt columns surface in JS as `bigint`; anything crossing a JSON boundary is
  serialised as a string (as `observationId` is).
- `ObservationStatusEvent.observationId` is `BigInt` — widening matches the
  parent.
- Entity uids are unguessable and safe to expose; observation ids are sequential
  and enumerable — acceptable, they are not a security boundary.

## Future migration trigger

- **Multi-region writers**: sequences would need range allocation or a move to
  uuidv7.
- **Id exhaustion**: 2^63 — effectively never.
- **Partitioning by `receivedAt`**: Postgres requires the partition key in the
  primary key; the PK would become `(id, receivedAt)` or the fact table would
  move to a composite PK — a design change with its own ADR.
