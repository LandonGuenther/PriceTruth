# Performance baseline

Measured 2026-09-11 on the overnight foundation branch against a **disposable synthetic
database** (`pricetruth_load`, PostgreSQL 16 in Docker on the development VM, default
`postgres:16` configuration, no tuning). Synthetic rows were generated by
`apps/api/scripts/loadgen.ts` (seeded PRNG, deterministic) and measured by
`apps/api/scripts/bench.ts`. Nothing here is real retailer history.

Both scripts refuse to run unless the database name ends in `_load` or
`PRICETRUTH_ALLOW_SYNTHETIC_LOAD=1` is set. Hardware: single shared VM; absolute numbers
are only meaningful relative to each other and as a trend across sizes.

## Method

- Listings: `max(200, N / 500)` (10,000 at 5M), half Amazon / half Best Buy, one Product each,
  observations spread uniformly over the trailing 365 days with a bounded random price walk,
  20% carrying a reference price, 90% `STANDARD` / 10% `SALE`.
- Rows are written with `synthetic = false` **only in this disposable database** (flag
  `--as-real`) so the eligibility filters exercise the same plans as production data.
- Latency metrics: 50 listings sampled, each request timed **sequentially** with
  `process.hrtime`, HTTP paths through `app.inject` with `statusCode === 200` asserted and a
  unique client address per request so the per-IP rate limiter cannot interfere.
  p50 / p95 / max over the 50 runs.
- Plans: `EXPLAIN (ANALYZE, BUFFERS)` of the exact SQL shapes used by the hot paths.

An earlier run of the bench issued requests concurrently and let the `analysis` sample hit
the 120/min rate limiter (measuring 429s at ~3 ms). Those numbers were discarded; the tables
below are from the corrected sequential bench.

## Query plans (5M)

All seven hot-path shapes are index-driven; **no sequential scans** at any tested size.

- **Latest observation** — `Index Scan Backward` on `(listingId, effectiveAt)` with
  `LIMIT 1`; eligibility predicates are applied as a filter on the first rows. 4 buffers.
- **History (90/180 d)** — `Bitmap Index Scan` on `(listingId, effectiveAt >= …)` →
  bitmap heap scan → in-memory quicksort of a few hundred rows (~58 kB). The sort is on the
  index's own second column; PostgreSQL chooses bitmap + sort over an ordered index scan
  because the listing's rows are spread over ~9 heap pages. Sub-millisecond.
- **Evidence group-by** — bitmap scan of the listing's rows on the same index, hash
  aggregate over ≤ 8 groups.
- **Dedupe probe** — `Index Scan` on `(listingId, effectiveAt >= now()-1h)` with a filter on
  price/currency/source; 3 buffers.
- **Anomaly context** — `Index Scan Backward` on `(listingId, effectiveAt)` with
  `LIMIT 20`; 20 buffers.
- **Identity lookup** — `BitmapOr` of two probes on the unique `(type, value)` index.
- **Rollup scan** — forward `Index Scan` on the BIGINT primary key with `id > cursor`.

## Index review (after measurement)

Existing indexes were sufficient for every measured path; **no index was added**. Candidates
considered and rejected, with reasons:

- `(listingId, status, effectiveAt)` — would let the eligibility filter be an index
  condition, but the filter currently discards ~0 rows on realistic data (most rows are
  eligible) and the extra column would enlarge the 280 MB index for no measured gain.
- `(listingId, receivedAt)` — no query orders or filters by `receivedAt` per listing yet;
  the archive exporter partitions by `receivedAt` but scans by `id`.
- Indexes on `IdentifierAssertion(type, normalizedValue)` and
  `ListingDailyPrice(listingId, day)` exist from the migrations and are used.

Revisit when a trigger in `docs/SCALE_TRIGGERS.md` fires.

## Bottlenecks found and fixed during the sprint

1. **Daily rollup** was a per-(listing, day) query + upsert loop: ~660 listing-days/s, i.e.
   the 1M database took 830 s and the 5M database did not finish within 60 minutes. Rewritten
   as one set-based statement per batch (`unnest` pairs → aggregate with `percentile_cont` →
   `INSERT … ON CONFLICT DO UPDATE` → delete emptied days): 313 s for 2.73M listing-days,
   ~13× faster, identical results under the existing semantic tests.
2. **Bench methodology**: concurrent requests and rate-limiter 429s were inflating or
   invalidating latencies (see Method).

## Known costs not yet optimised (measured, acceptable for now)

- API-path ingest is ~85 ms p50 because one observation performs ~12 round trips (listing
  upsert, assertion upserts, dedupe probe, anomaly context, transactional insert + event,
  corroboration scan of the listing's 30-day rows). Fine for extension traffic (one
  observation per page view); batching or moving corroboration to the job runner is the
  first lever if ingest QPS matters.
- `analysis` loads every eligible row for the listing (≈500 here). It scales linearly with
  per-listing history; switching long ranges to `ListingDailyPrice` is the planned fix
  (see `docs/DATA_PLATFORM.md`).
- Full rollup from scratch is O(all rows); the incremental job only touches changed
  listing-days and is the normal mode.

## Appendix — 100K and 1M (corrected bench)

Per-request latency is essentially flat from 100K to 5M rows because every hot path is a
per-listing index range; what grows is per-listing history depth (~500 rows here at all
sizes) and the whole-table jobs (rollup, archive).

| Metric                           | 100K (200 listings) | 1M (2,000 listings)   | 5M (10,000 listings)     |
| -------------------------------- | ------------------- | --------------------- | ------------------------ |
| latest p50 / p95                 | 2.3 / 2.8 ms        | 2.4 / 2.8 ms          | 2.0 / 2.5 ms             |
| history 90 d p50 / p95           | 10.6 / 11.8 ms      | 11.0 / 12.0 ms        | 10.7 / 13.5 ms           |
| history 180 d p50 / p95          | 14.7 / 16.2 ms      | 15.7 / 19.5 ms        | 15.0 / 19.2 ms           |
| analysis p50 / p95               | 15.3 / 17.0 ms      | 15.4 / 18.5 ms        | 15.1 / 18.7 ms           |
| identity lookup p50 / p95        | 1.4 / 1.6 ms        | 1.4 / 2.3 ms          | 0.8 / 2.5 ms             |
| bulk load                        | 14,176 rows/s       | 14,792 rows/s         | 14,011 rows/s            |
| API-path ingest p50 / p95        | 66.7 / 145.9 ms     | 86.7 / 170.0 ms       | 84.7 / 148.2 ms          |
| full daily rollup                | 2.7 s (55,953 days) | 65.3 s (547,435 days) | 313.5 s (2,729,183 days) |
| archive export per 50k-row batch | 5.1 s · 13.5 MB     | 5.1 s · 13.5 MB       | ~4.4 s · 13.5 MB         |
| table + indexes                  | 21 MB               | 212 MB                | 1,061 MB                 |

Archive export cost is per batch and independent of table size, as expected for an
`id`-cursor scan. (In the 5M run one of the two sampled batches already existed and was
idempotently skipped, so the raw log's per-row figure for that run is halved; the per-batch
figure above is the consistent one.)

## Post-production-hardening re-run — 1,000,200 observations (2,000 listings)

Same bench script, run with the production request path intact:
`LOG_LEVEL=info` (one JSON access-log line per request) and the real
per-IP rate limiter enabled — each of the 200 measured requests carries a
unique `remoteAddress` (`10.0.x.x`) so the limiter is exercised but never
trips. Sequential, same 50-listing sample, in-process `app.inject`.

| Metric                                                  | Pre-hardening 1M   | Post-hardening 1M         | Δ p95 |
| ------------------------------------------------------- | ------------------ | ------------------------- | ----- |
| latest p50 / p95                                        | 2.4 / 2.8 ms       | 2.1 / 2.8 ms              | 0%    |
| history 90 d p50 / p95                                  | 11.0 / 12.0 ms     | 11.4 / 14.5 ms            | +21%  |
| history 180 d p50 / p95                                 | 15.7 / 19.5 ms     | 16.4 / 19.6 ms            | +1%   |
| analysis p50 / p95                                      | 15.4 / 18.5 ms     | 17.1 / 19.3 ms            | +4%   |
| identity lookup p50 / p95                               | 1.4 / 2.3 ms       | 1.4 / 1.6 ms              | −30%  |
| full daily rollup                                       | 65.3 s (547k days) | 76.5 s (547k days)        | +17%  |
| archive export (150k rows, 3 batches incl. checkpoints) | 5.1 s/50k          | 11.8 s total (~3.9 s/50k) | −23%  |
| table + indexes                                         | 212 MB             | 212 MB                    | —     |

No p95 regression exceeds the 25% flag threshold (largest: history90 +21%,
within n=50 sequential noise). The hardening additions — access log, metrics
hooks, version/request-id headers, rate-limit accounting — cost ≈0.5–1.5 ms
per request at 1M rows. Rollup +17% likely reflects the added
signal/heartbeat checks per batch plus log I/O, still ~7.2k listing-days/s.
